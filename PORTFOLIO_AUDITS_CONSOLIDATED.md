# ИИ 3 — полный ответ (backend / качество / security)

Итог: сайт технически выше среднего для личного портфолио, но как инструмент продажи вас работодателю он пока слабее, чем сам код.

Моя оценка:

- качество кода — 7/10;
- визуальный дизайн — 7/10;
- адаптивность и UX — 7.5/10;
- производительность — 7/10;
- убедительность портфолио — 5.5/10;
- общая — примерно 6.8/10.

## Что сделано хорошо

- Нормальное разделение на страницы, компоненты, хуки и данные.
- Ленивые маршруты, Error Boundary, тёмная тема без заметного FOUC, локальный шрифт и адаптивный avatar.
- Хорошая база accessibility: семантические заголовки, `aria-live`, reduced motion, управление меню с клавиатуры.
- Есть CSP, security headers и фильтрация внешних URL.
- ESLint и проверка циклических импортов проходят.
- Все 36 unit-тестов проходят.
- Сборка успешна, браузерная консоль опубликованного [сайта](https://www.akbar02work.xyz/) чистая.
- На 390×844 нет горизонтального переполнения главной страницы, мобильное меню корректно блокирует фон и удерживает фокус.

То есть это не плохой «AI-generated лендинг». Видно, что проект дорабатывался и проверялся.

## Главные проблемы кода

1. TypeScript фактически не является quality gate.

В `tsconfig.app.json` включён строгий режим, но `tsc --noEmit` падает: неправильный `fetchpriority`, проблемы с fallback-ветками `matchMedia`, таймерами и тестовыми globals. При этом CI typecheck не запускает.

Особенно показателен `Hero.tsx`: React ожидает `fetchPriority`, а не `fetchpriority`.

2. Bundle-budget создаёт ложное чувство контроля.

Текущая production-сборка:

- initial JavaScript — около 135 KB gzip;
- CSS — около 10.6 KB gzip;
- `vendor` — 312 KB raw / 102 KB gzip.

Для портфолио это приемлемо, но не идеально. `check-bundle.js` проверяет только `index-*` и игнорирует основной vendor chunk. Поэтому отчёт говорит «budget OK», хотя проверяет не весь initial payload.

Вероятный кандидат на вынос — синхронно импортируемый Sentry в `monitoring.ts`. Его можно загружать динамически только при наличии DSN.

3. Закрытое меню темы остаётся в accessibility tree.

В `Navbar.tsx` меню скрывается через `opacity` и `pointer-events`, но его пункты продолжают существовать и могут попадать в клавиатурную навигацию. Лучше условно рендерить меню либо использовать `hidden`, `aria-hidden` и корректный `tabIndex`.

4. На project detail есть 2 px горизонтального переполнения.

Причина — невидимое меню выбора темы, центрированное относительно кнопки у правого края. Лучше выравнивать этот dropdown через `right-0`, а не `left-1/2`.

5. Кеширование ассетов не оптимально.

Даже хешированные JS-файлы отдаются с `Cache-Control: max-age=0, must-revalidate`. В `vercel.json` стоит добавить отдельное правило `immutable, max-age=31536000` для `/assets/*`.

## Главная проблема — не код, а содержание

Сайт утверждает, что вы создаёте production-ready приложения, но почти не показывает доказательств.

В `projectCatalog.ts`:

- всего два проекта;
- используются placeholder-изображения;
- нет измеримых результатов;
- нет вашей конкретной роли;
- нет архитектурных схем, компромиссов и инженерных решений.

Поля `results` и `roadmap` существуют, но `ProjectDetailsSection.tsx` вообще их не выводит.

Дополнительно универсальная карточка всегда рисует телефонный mockup `9:19` в `ProjectCard.tsx`. Для Android-приложения это уместно, для Python-бенчмарка SecBench — нет. Из-за этого сайт выглядит шаблонным.

## Что я бы изменил в дизайне

Лучшее направление: не «портфолио с красивыми анимациями», а компактный engineering casebook.

1. Сделать первый экран короче.

Сейчас mobile hero занимает примерно 1150 px, а первая работа начинается только около 1800 px. Уменьшить портрет до 220–240 px либо использовать компактный горизонтальный crop.

2. Сразу после hero показывать проекты.

Секция About из двух абзацев занимает около 585 px. Её можно перенести ниже проектов или сократить до короткого блока.

3. Убрать carousel.

Для двух проектов сетка из двух больших карточек намного лучше: пользователь сразу видит обе работы и может сравнить их. Автопереключение здесь только прячет контент.

4. Использовать реальные доказательства.

Для каждого кейса:

- проблема;
- ваша роль;
- ограничения;
- ключевое инженерное решение;
- 2–4 настоящих скриншота;
- схема архитектуры;
- подтверждённый результат;
- GitHub / APK / Play Store, если доступны.

5. Убрать «Coded by AI».

Фраза в `Footer.tsx` снижает ощущение вашей ответственности за результат. Лучше: `Designed and built by Akbar` или вообще ничего. Прозрачность про AI можно оставить в README.

6. Сделать визуальный язык менее шаблонным.

Сохранить монохромную основу и портрет, но убрать часть плавающих логотипов. Добавить один акцентный цвет — Android green или Kotlin violet — и применять его только к важным элементам и кейсам.

## SEO

Project pages динамически меняют метаданные через React Helmet, но сервер возвращает для `/projects/voicenotes` метаданные главной страницы. Социальные превью и часть crawlers увидят не VoiceNotes, а общий portfolio title.

Нужно prerender/SSG для трёх публичных маршрутов, отдельные canonical URL и актуальная sitemap. Сейчас даты в `sitemap.xml` всё ещё стоят за 2024 год.
