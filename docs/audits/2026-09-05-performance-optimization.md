# Оптимизация производительности portfolio — 5 сентября 2026

Работа выполнена локально в `portfolio`. Baseline — состояние **после предыдущего
аудита в этой задаче**, включая его незакоммиченные исправления. Эти изменения
сохранены. Другие проекты не исследовались; commit, push, deploy, изменение
внешних сервисов и добавление зависимостей не выполнялись.

## Методика и воспроизводимость

- Production-сборки обоих приложений: Node 24.20.0, Vite 8.1.5. Профилировщики:
  Node 26.0.0, Playwright Chromium 149.0.7827.55, macOS / Apple M4.
- Холодная загрузка: отдельный browser context на каждый прогон, отключённый
  HTTP-кэш, 4× CPU slowdown, 150 мс latency, 200 000 байт/с download, gzip.
  По **3 последовательных прогона** на каждую из 6 комбинаций страницы/viewport.
  Таблицы показывают медианы, а не лучший прогон.
- Desktop: 1440×1000, DPR 1; mobile viewport: 390×844, DPR 2. Это эмуляция
  viewport/плотности и ограничений CPU/сети, а не физический телефон.
- `ready`: первый animation frame с `h1` после снятия `body.is-loading`.
  Это наличие разметки и разблокировка прокрутки, **не TTI** и не окончание intro.
  FCP, LCP, CLS и long tasks записываются до `ready + 2,5 с`.
- «Блокировка» ниже — сумма `max(0, longTask.duration − 50 мс)` в этом окне.
  Это диагностическая величина, **не Lighthouse TBT и не INP**.
- Runtime-профили: 4× CPU, сеть без ограничения; 4 с простоя, 4 с прокрутки
  сверху вниз, затем 80 перемещений указателя для Creative. Сохранены CDP CPU
  profiles, длительности Script/Layout/RecalcStyle, счётчики DOM/WebGL и React.
- Версии переключаются настоящими ссылками, с включённым кэшем и теми же
  ограничениями CPU/сети. Время считается от начала document navigation до
  появления `h1` и удаления прелоадера; окончание hero intro не ожидается.
- Headless Chromium использовал **ANGLE / SwiftShader**, программный WebGL.
  Поэтому здесь нет утверждений об аппаратном FPS, расходе батареи или GPU-time
  на реальном устройстве. Инструментирование само добавляет накладные расходы.

Метрики опираются на [CDP CPU throttling](https://chromedevtools.github.io/devtools-protocol/tot/Emulation/#method-setCPUThrottlingRate)
и [PerformanceLongTaskTiming](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceLongTaskTiming).
Локальный сервер применяет ограниченный набор правил `vercel.json`; это не
эмулятор Vercel edge, HTTP/2/3, Brotli, TLS или географической задержки.

Снимок исходной сборки, исходные hashes/diff, сырые JSON, `.cpuprofile`, логи и
скриншоты находятся в игнорируемом `logs/performance-2026-09-05/`:

- `baseline-dist/`, `before-source/`, `start-hashes.json`, `start-diff.patch`;
- `baseline/` и `final/`: холодные загрузки и переходы;
- `react-baseline/`, `creative-runtime/`, `pre-webkit/`, `final/`: промежуточные
  и итоговые runtime-профили;
- `image-preload/`, `images/`, `priority-auto/`, `no-webgl-probe/`: изолированные
  проверки причин; WebGL выключался **только в диагностическом контексте**;
- `webkit-network.json`, `visuals/geometry.json`, `visuals/*.png`.

Повторить на новой сборке, последовательно, из корня репозитория:

```bash
npm run build
node scripts/profile-performance.mjs after
node scripts/profile-interactions.mjs after
node scripts/profile-navigation.mjs after
PERF_FLOW=projects node scripts/profile-navigation.mjs after
```

По умолчанию результаты пишутся в `logs/performance/after/`. Для исходного
baseline этого аудита:

```bash
PERF_OUTPUT_DIR=logs/performance-2026-09-05 \
```

## Холодная загрузка: до → после

Все времена — мс. Ресурсы — КиБ сжатых тел загруженных ресурсов, без HTML
документа и HTTP-заголовков; сравнивается одинаковое окно наблюдения.

| Сценарий | FCP | LCP | ready | Блокировка | Ресурсы, КиБ |
| --- | ---: | ---: | ---: | ---: | ---: |
| Business desktop | 748 → 732 | **2076 → 1664** | 1572 → 1642 | 78 → 46 | 284,8 → 258,1 |
| Business mobile | 724 → 732 | **2112 → 1696** | 1547 → 1683 | 61 → 42 | 293,4 → 266,7 |
| VoiceNotes desktop | 720 → 752 | **2216 → 1644** | 1541 → 1627 | 56 → 49 | 318,5 → 318,6 |
| VoiceNotes mobile | 728 → 732 | **2212 → 1640** | 1536 → 1628 | 50 → 46 | 318,5 → 318,6 |
| Creative desktop | 1588 → 1580 | 1588 → 2668* | **3395 → 2605** | **821 → 31** | 200,8 → 200,9 |
| Creative mobile gate | 1076 → 1084 | 1076 → 1084 | 1070 → 1074 | 0 → 0 | 124,0 → 124,0 |

LCP главной улучшился на **20%**, страницы проекта — на **26%**. Preload делит
полосу с JavaScript: Business `ready` наступает на 70–136 мс позже, проект — на
86–92 мс позже. Это явный компромисс: главный визуальный контент появляется на
412–572 мс раньше. Forced high priority у preload был отдельно проверен и убран:
он задерживал раннюю отрисовку шрифтов, не улучшая LCP. Приоритет самого hero img
сохранён. Мелкие изменения FCP/long tasks вне Creative не трактуются как отдельное
доказанное ускорение CPU.

\* В исходном Creative LCP-кандидатом был **текст прелоадера**. После изменений
кандидат сменился на контент страницы. Сравнивать эти два числа как одинаковый
контент нельзя. Более полезны одинаково определённые `ready` (−23%) и блокировка
(−96%). Длительности прелоадера, шторки и видимого intro не сокращались.

CLS: 0 на Business/VoiceNotes/mobile gate, около 0,005 на Creative desktop до и
после. Незначительное дрожание значений Creative связано с анимацией/шрифтами.

## Найденные причины и исправления

### 1. Изображения обнаруживались после исполнения приложения

В baseline загрузка портрета и обложки начиналась примерно на 1,5 с, после
основного JS. HTML теперь содержит preload только нужного изображения маршрута.
Главная использует общий с React `srcset/sizes`; проект — реально существующий
AVIF cover. Нет preload всех слайдов или портрета на странице проекта.

Изолированная проверка одного preload портрета уже дала LCP 2076 → 1672 мс на
desktop и 2112 → 1696 мс на mobile. Браузерные тесты проверяют выбор фактического
варианта, единственную передачу тела и работающий fallback при отсутствии AVIF.

Для responsive preload `href` опущен: WebKit 26.5 иначе дополнительно запрашивал
полный `avatar.webp`. Это воспроизведено локально и соответствует
[ошибке WebKit 320786](https://bugs.webkit.org/show_bug.cgi?id=320786).
Синтаксис без `href` описан в [документации WebKit](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/).

### 2. WebKit загружал неиспользуемые fallback-изображения

При создании `<img>` React 18 устанавливает атрибуты до присоединения к
`<picture>`. WebKit начинает запрос сразу: сначала `src`, затем `srcset`, затем
выбирает `<source>`. Неверный порядок `loading`, `sizes`, `srcset`, `src` также
нарушал ожидаемую ленивую загрузку. Это совпадает с
[WebKit 276586](https://bugs.webkit.org/show_bug.cgi?id=276586).

Доказательства на WebKit 26.5, viewport 390/1440, DPR 1, без сетевого throttling:

- Портрет mobile: дополнительно передавались три PNG суммарно **178,7 КиБ**;
  desktop: два PNG, **148,4 КиБ**. В финале этих запросов нет; используется WebP.
- На странице проекта запрашивались оба формата всех шести экранов. В финале
  исчезли шесть ненужных WebP, суммарно **158,3 КиБ**; AVIF и fallback сохранены.

`loading="lazy"` теперь устанавливается до URL. Для важных `<picture>` маленький
общий ref переводит изображение в `eager` синхронно после присоединения к DOM,
до paint. Это не откладывает hero/галерею до IntersectionObserver или скролла;
тесты проверяют итоговый `loading="eager"` и видимый декодированный контент.

У WebKit некоторые Resource Timing записи AVIF имеют нулевые размеры; поэтому
проценты общего трафика Safari по ним не вычислялись. Экономия выше относится
к исчезнувшим fallback-файлам с подтверждёнными запросами и размерами. WebKit
может сообщить два события одного preload, включая запись без передачи тела;
тест контролирует варианты и реальные transfer entries, а не число событий API.

### 3. Рамка телефона была существенно больше отображаемого размера

В карточке используется 176/256 CSS px, но передавалась рамка шириной 1620 px.
Добавлен WebP 512 px, созданный из исходного PNG существующим Sharp:
**37,4 → 10,5 КиБ (−72%)**. Полный вариант остаётся для большей плотности пикселей.
Сам исходный PNG и скриншоты не изменены. При ошибке responsive URL `srcset`
удаляется перед переходом на PNG, чтобы браузер действительно применил fallback.

Это уменьшило холодный payload главной примерно на **26,7 КиБ (9%)** в обоих
viewport. Выбор размера проверен браузерами; рамка визуально сравнена до/после.

### 4. Creative пересчитывал стили всего документа при скролле

`ScrollTrigger` записывал `--scroll` на `documentElement`; `ScrollNav` тут же читал
его через `getComputedStyle`. Значение потреблялось только навигацией и shader.
Они теперь используют уже существующий общий ref. Лишняя наследуемая CSS
переменная удалена. Геометрия карточек читается перед записью их стилей.

В одинаковом 4-секундном скролле `RecalcStyleDuration`: **618 → 115 мс (−81%)**.
Промежуточные повторения давали 96–106 мс; это диапазон локального шума, а не
основание приписывать точный процент одной небольшой перестановке операций.
Геометрия, opacity, scale и blur карточек в 0%, 50%, 100% pin-прогресса совпали.

### 5. Таймеры перерисовывали всю Creative-страницу

Часы и мигающий символ перенесены в маленькие компоненты с собственным состоянием;
`Intl.DateTimeFormat` создаётся один раз на lifecycle. `PortfolioPage` перестал
рендериться от этих таймеров: **12 → 0 рендеров за 4 с простоя**, 11 → 0 при
скролле, 16 → 0 в сценарии pointer. Нужные изменения props по-прежнему доходят.

Счётчик прелоадера обновляет свой текст через ref, а полоса использует `scaleX`
вместо изменения ширины. Рендеры прелоадера при старте: **41 → 4**. Внешний вид,
процент, session-семантика и длительность 0,9 с сохранены.

### 6. WebGL работал под непрозрачным прелоадером и вычислял пустой след

Canvas теперь запускается при готовности страницы, до выхода шторки. Пока не
было движения указателя, trail FBO остаётся нулевым: при нулевом предыдущем
состоянии и `u_moving=0` shader возвращает ноль. Этот проход пропускается;
атмосферный display-проход остаётся. После первого pointer input оба прохода
работают как раньше. Разрешение, DPR, шейдеры и лимиты кадров не снижались.

Attribute locations запоминаются после linking: **404 вызова `getAttribLocation`
за 4 с простоя → 0**; на инициализации остаются два. До первого pointer input
нужен один draw вместо двух на кадр. Регрессионный WebGL-тест проверяет оба режима
и активацию следа после движения. Он Chromium-only; общий Creative E2E выполняется
также в Firefox/WebKit.

Контроль без WebGL уменьшал baseline-блокировку с 821 до 5 мс. Финальная версия
**с сохранённым WebGL** даёт 31 мс. Это доказательство причины стартовой блокировки
в данном стенде; аппаратные GPU и длительную работу на батарее нужно мерить отдельно.

### 7. Повторные посещения снова передавали шрифты и изображения

Для локальных шрифтов, портретов, project images и mockups добавлен
`Cache-Control: public, max-age=86400`. Хэшированные JS/CSS сохраняют годовой
immutable cache; HTML, CV и метаданные не получили длительный cache override.
Правила ресурсов ограничены путями/расширениями и проверены против HTML проекта.

| Переход | Готовность, мс | Переданные ресурсы, КиБ |
| --- | ---: | ---: |
| Business → Creative, впервые | 3480 → 3181 | 203,5 → 203,5 |
| Creative → Business, повторно | 466 → 397 | **165,9 → 0,9** |
| Business → Creative, повторно | 674 → 616 | **59,8 → 0** |

HTML-документ в последней колонке не учтён и запрашивается заново. Остаток Business
— маленький theme-init и локальная попытка загрузить SpeedInsights. Нулевой
resource transfer не означает отсутствие HTML-запроса или JavaScript-исполнения.

Отдельный SPA-сценарий с завершением шторки и декодированным первым экраном:
главная → VoiceNotes **974 → 969 мс**, назад к списку **929 → 929 мс**; новые
ресурсы соответственно 94 → 94 КиБ и 0 → 0 КиБ. Разница в пределах шума,
ускорение этого перехода не заявляется. Здесь доминирует сохранённая анимация,
а первый экран уже загружен карточкой главной. Дополнительный route chunk или
агрессивная подгрузка остальных экранов не добавлялись.

Цена политики: изменение содержимого по прежнему URL может быть не видно до суток.
При срочном обновлении изображения/шрифта нужно поменять имя файла. Production
поведение нужно подтвердить после отдельно разрешённого релиза по
[правилам Vercel headers](https://vercel.com/docs/project-configuration/vercel-json#headers).

- Дополнительная сборка с `VITE_BASE_URL=/portfolio-check/`: оба image preload
  получили правильный prefix; затем повторно прошёл полный CI обычной сборки.
- Визуально просмотрены Business, mobile VoiceNotes, рамка, Creative hero и
  начало/середина/конец горизонтального pin. Продуктовые тексты/публикация проектов
  не менялись; desktop-only gate Creative сохранён.
- Diff проверен отдельно относительно состояния в начале этого этапа и относительно
  Git. Изменения предыдущего аудита сохранены; новые исходники, ресурсы, отчёты и
  измерительные артефакты созданы только внутри `portfolio`.

Не внедрены без измеримого основания: новый route splitting Business, замена
GSAP/Lenis/React, content-visibility с искусственными высотами, снижение WebGL
качества, удаление favicon-анимации, пересжатие портрета в AVIF и шрифтовой дизайн.
В runtime Business/VoiceNotes нет сопоставимого с Creative CPU-bottleneck;
дополнительный lazy chunk мог бы добавить waterfall при прямом входе в проект.

Начальный JS/CSS Business: **121,04 → 121,18 КиБ gzip**, полный Creative:
**123,91 → 123,95 КиБ**, ниже бюджета 150 КиБ. Небольшая прибавка не скрывается: ускорение
получено доставкой ресурсов и уменьшением runtime-работы, не сокращением bundle.
Sentry уже вынесен в отдельный динамический chunk; если production задаёт DSN,
его примерно 155 КиБ gzip могут изменить сетевой профиль. Production-настройки
Sentry/SpeedInsights и реальные RUM-метрики не проверялись и не изменялись.

Остаются отдельными проверками: физические Safari/iPhone/Android и слабые ноутбуки,
аппаратный WebGL/FPS/энергопотребление, INP реальных сессий, Vercel CDN/cache hit,
сетевые ошибки на длительных сессиях и доставка обновлённых unversioned assets.
